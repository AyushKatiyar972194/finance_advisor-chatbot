\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
In the modern economic landscape, financial planning has shifted from manual bookkeeping to digital advisory systems. However, existing personal finance applications are typically fragmented, requiring individuals to traverse independent platforms to calculate budgets, simulate mutual fund investments, compute loan EMI options, or compare tax regime implications. Furthermore, cloud-based Large Language Model (LLM) advisory services incur high subscription costs and raise significant data privacy concerns. 

This project presents an AI-Powered Personal Finance Advisor Chatbot utilizing a Multi-Agent Architecture built in n8n and powered locally by Ollama (Llama 3.2 3B). The system deploys a sequence of specialized role-playing agents (Budget Advisor, Investment Advisor, Debt Advisor, Tax Advisor, and Chief Financial Planner) that collaborate to analyze a user's single-line financial query. 

Dynamic math operations are executed via custom JavaScript calculator tools, with a Zod-aligned permissive schema mapping ([number, string, null]) to prevent structural type-mismatch failures common in local LLM tool calling. The final report is synthesized as a structured JSON object containing a summary, recommendations, risks, and a concrete action plan, returned seamlessly to a webhook response. This approach maintains complete data privacy, eliminates API token costs, and provides comprehensive, integrated advisory reports.

\chapter{Introduction}
\pagenumbering{arabic}
\setcounter{page}{1}
Artificial Intelligence has transitioned from predictive modeling to agentic orchestration, where Large Language Models (LLMs) act as reasoning engines capable of planning, executing tools, and synthesizing multi-step results. In the domain of personal finance, traditional advisors are costly, while standard budgeting applications remain highly fragmented. 

Users must compile metadata manually across budget calculators, SIP compounding estimators, loan amortization spreadsheets, and income tax calculators. This fragmented procedure introduces cognitive overload and delays critical financial decisions.

\section{Problem Statement}
Managing personal finances remains a highly fragmented and cognitively demanding task for individuals. Organizing a cohesive financial strategy typically requires traversing multiple independent financial portals or static spreadsheets. The primary challenges in existing systems include:
\begin{itemize}
    \item \textbf{Information Fragmentation:} Essential parameters regarding savings behavior, investment compounding, debt liabilities, and tax bracket efficiency reside on isolated systems, forcing manual correlation.
    \item \textbf{Schema and Format Failures in AI Tool Calling:} Local and lightweight LLMs (such as Llama 3.2 3B) often output numerical arguments as strings (e.g., \texttt{"5000"} instead of \texttt{5000}), which fails strict type constraints in standard LangChain structured schemas.
    \item \textbf{Data Privacy Risks:} Sending detailed personal financial data (income, expenditures, outstanding debts, and tax brackets) to cloud-hosted LLM APIs exposes users to privacy and security hazards.
    \item \textbf{High Cloud Token Costs:} Running complex multi-agent reasoning chains with multiple iterations on commercial models (e.g., GPT-4) incurs high recurrent operational costs.
    \item \textbf{Lack of Integrated Synthesized Reports:} Existing planners fail to synthesize budgeting targets, compounding wealth returns, debt avalanche prioritizations, and tax regime recommendations into a single cohesive client report.
\end{itemize}
This project directly resolves these issues by building an automated, sequential multi-agent workflow in n8n that routes queries through custom mathematical tools with relaxed schemas, running fully locally to guarantee data privacy.

\section{Scope of the Project}
The scope of this project encompasses the design, implementation, and verification of a multi-agent personal finance chatbot system:
\begin{itemize}
    \item \textbf{Sequential Agent Chain:} A pipeline consisting of five specialized agents: Budget, Investment, Debt, Tax, and Financial Planner.
    \item \textbf{Custom JS Calculator Tools:} Four mathematical calculators (\texttt{budget\_calculator}, \texttt{sip\_calculator}, \texttt{emi\_calculator}, \texttt{tax\_calculator}) with flexible string/number parsing.
    \item \textbf{Shared Chat Memory:} Integration of a shared Window Buffer Memory node using a unique \texttt{session\_id} to persist context across the sequential agent steps.
    \item \textbf{Local LLM Integration:} Configuration of Ollama hosting \texttt{llama3.2:3b} on local CPU resources to remove external token fees and secure user data.
    \item \textbf{Unified API Access:} Development of a Webhook Trigger node accepting POST payloads and returning a structured JSON advisory layout via a Respond to Webhook node.
\end{itemize}

\section{Advantages of the Proposed System}
\begin{itemize}
    \item \textbf{Automated Financial Synthesis:} Compiles analysis from budget, investment, debt, and tax domains into one unified client report.
    \item \textbf{Robust Local Parameter Validation:} Relaxed Zod input schemas accept numbers, strings, or nulls, letting custom tools safely parse inputs and prevent LLM tool-calling crashes.
    \item \textbf{Zero Token Fees:} By executing Llama 3.2 locally on consumer hardware, the system runs indefinitely without API costs.
    \item \textbf{Complete Data Privacy:} Personal financial data never leaves the host machine, matching corporate compliance and privacy guidelines.
\end{itemize}

\section{Limitations of Existing Systems}
\begin{itemize}
    \item \textbf{Static Budget Templates:} Rigid estimators require perfect inputs and fail to parse natural language queries (e.g., "I earn 50k and spend 30k").
    \item \textbf{Cloud API Dependence:} Standard multi-agent systems rely on cloud endpoints (OpenAI/Anthropic) which can crash on network loss and incur usage costs.
    \item \textbf{Fragmented Context:} Most calculators operate in silos; an investment simulator does not inspect a user's monthly budget surplus, leading to impractical compounding recommendations.
\end{itemize}

\section{Objective of the Project}
The primary objective of this project is to develop a production-ready, local multi-agent chatbot that accepts user financial queries, executes custom calculation tools safely using relaxed schemas, and returns a JSON report mapping budget splits, SIP growth, EMI payoff, and tax regimes.

\section{Custom JavaScript Calculator Tools}
Below is the JavaScript code embedded in the \texttt{sip\_calculator} node, illustrating how the inputs are parsed:
\begin{lstlisting}[language=JavaScript, caption=sip\_calculator JS Implementation]
try {
  let sip = null;
  let rate_annual = null;
  let years = null;
  
  if (query && typeof query === 'object') {
    sip = typeof query.monthly_investment === 'number' ? query.monthly_investment : (parseFloat(query.monthly_investment) || null);
    rate_annual = typeof query.expected_return_rate === 'number' ? query.expected_return_rate : (parseFloat(query.expected_return_rate) || null);
    years = typeof query.years === 'number' ? query.years : (parseInt(query.years) || null);
  }
  
  if (sip === null || rate_annual === null || years === null) {
    let text = '';
    if (typeof query === 'string') {
      text = query;
    } else if (query && typeof query === 'object') {
      text = query.query || query.input || '';
    }
    
    const parseNum = (matchResult) => {
      if (!matchResult) return null;
      let val = parseFloat(matchResult[1]);
      const unit = (matchResult[2] || '').toLowerCase();
      if (unit.startsWith('k')) val *= 1000;
      else if (unit.startsWith('l')) val *= 100000;
      else if (unit.startsWith('m')) val *= 1000000;
      return val;
    };
    
    if (sip === null) {
      sip = parseNum(text.match(/(?:sip|monthly|invest|saving)\D*(\d+(?:\.\d+)?)\s*(k|lakh|l|m)?/i));
    }
    if (rate_annual === null) {
      const pctMatch = text.match(/(\d+(?:\.\d+)?)\s*%/);
      if (pctMatch) {
        rate_annual = parseFloat(pctMatch[1]);
      } else {
        const rateMatch = text.match(/(?:rate|return|interest|yield)\D*(\d+(?:\.\d+)?)/i);
        if (rateMatch) rate_annual = parseFloat(rateMatch[1]);
      }
    }
    if (years === null) {
      const yrMatch = text.match(/(\d+)\s*(?:year|yr|y)/i);
      if (yrMatch) {
        years = parseInt(yrMatch[1]);
      } else {
        const yearsMatch = text.match(/(?:year|duration|time|period)\D*(\d+)/i);
        if (yearsMatch) years = parseInt(yearsMatch[1]);
      }
    }
  }
  
  if (sip === null || rate_annual === null || years === null) {
    const missing = [];
    if (sip === null) missing.push('monthly_investment');
    if (rate_annual === null) missing.push('expected_return_rate');
    if (years === null) missing.push('years');
    return `Error: Missing required inputs for SIP calculation. Required: ${missing.join(', ')}.`;
  }
  
  const rate_monthly = rate_annual / 12 / 100;
  const months = years * 12;
  const total_invested = sip * months;
  const maturity_value = sip * ((Math.pow(1 + rate_monthly, months) - 1) / rate_monthly) * (1 + rate_monthly);
  const estimated_returns = maturity_value - total_invested;
  
  const fmt = (num) => num.toLocaleString('en-US', { minimumFractionDigits: 2, maximumFractionDigits: 2 });
  
  return `Monthly SIP: INR ${fmt(sip)}
Tenure: ${years} years (${months} months)
Expected Return Rate: ${rate_annual.toFixed(2)}%
Total Invested: INR ${fmt(total_invested)}
Maturity Value: INR ${fmt(maturity_value)}
Wealth Gained: INR ${fmt(estimated_returns)}`;
} catch (e) {
  return 'Error: ' + e.message;
}
\end{lstlisting}

\section{Resolution of Tool Schema Validation Failures}
During early development, the workflow threw the following schema validation errors:
\begin{lstlisting}[language=bash, caption=Tool Schema Validation Error]
Received tool input did not match expected schema 
✖ Expected number, received null -> at monthly_investment
\end{lstlisting}
This occurred because the local LLM passed arguments as string quotes (e.g., \texttt{"5000"}) or omitted them (e.g., \texttt{null}). 

The error was successfully resolved by:
\begin{enumerate}
    \item Rewriting the tool input schemas to allow a union of types: \texttt{["number", "string", "null"]}.
    \item Modifying the custom JS tool scripts to execute explicit type coercion: \texttt{parseFloat(query.monthly\_investment)}.
    \item Confirming the database is updated with \texttt{schemaType: "manual"}, forcing the n8n core parser to read the \texttt{inputSchema} structure.
\end{enumerate}
